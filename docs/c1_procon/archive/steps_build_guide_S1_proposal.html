Phase 1

Build AOP-BenchPos, your dataset

Everything downstream depends on this being right. Rushing this phase is the single most common way this kind of project goes wrong later.

STEP 1.2

Standardise every source into one common table

Every source formats sequences and labels differently. Before anything else can happen, they all need to become one pandas DataFrame with the same columns.

# src/data_prep.py
import pandas as pd

def clean_sequence(seq: str) -> str:
    return str(seq).upper().replace("~", "").strip()

def load_source(path, source_name):
    df = pd.read_csv(path)
    df["sequence"] = df["Sequence"].apply(clean_sequence)
    df = df[(df["sequence"].str.len() >= 3) & (df["sequence"].str.len() <= 50)]
    df["source_db"] = source_name
    return df[["sequence", "source_db"]].drop_duplicates()

# repeat for each of the 5 sources, then:
merged = pd.concat([anoxpepred_df, multiaop_df, biopep_df, dfbp_df, peptipedia_df],
                    ignore_index=True)
merged.to_csv("data/processed/merged_raw.csv", index=False)

Every source's raw file has different column names — check each one manually before writing its loader; don't assume they all have a column literally called Sequence.

Checkpoint One CSV, one sequence column, one source_db column, no sequence outside 3–50 amino acids.
STEP 1.3

Remove near-duplicate sequences with CD-HIT

Multiple databases will contain the exact same peptide, sometimes with tiny spelling differences. Left in, these inflate your peptide count and can leak between train and test later. CD-HIT collapses anything ≥90% identical into one representative sequence.

# install (Linux/WSL or Colab)
sudo apt-get install cd-hit
# or: conda install -c bioconda cd-hit

# convert your merged table to FASTA first, then run:
cd-hit -i merged.fasta -o merged_cdhit90.fasta -c 0.90 -n 5 -M 0 -d 0

On Windows, run this step inside WSL or a Colab cell — CD-HIT doesn't have a native Windows build.

Checkpoint The output FASTA has noticeably fewer sequences than the input, and merged_cdhit90.fasta.clstr exists (it lists what got merged into what).
STEP 1.4

Label every sequence with its mechanism tier

This is the labelling scheme the whole component is built on — get it right once here and every later stage inherits it correctly.

  • Tier 1 (FRS) — from AnOxPePred, where the FRS column = 1.
  • Tier 2 (MC) — from AnOxPePred, where the Chelator column = 1.
  • Tier 3 (General) — everything else: BIOPEP-UWM / DFBP / Peptipedia records tagged "antioxidant" with no specific assay behind them.

Add a tier column to your merged table and save it. From this point on, Tier 3 is read-only — it goes into evaluation later, never into a training pair.

Common mistake Don't guess a tier for a sequence that only has a generic "antioxidant" tag. If you can't point to an assay type behind a label, it's Tier 3 — full stop.
STEP 1.5

Check you actually have enough data

Do this before writing a single line of model code — it changes how much of the rest of the pipeline you need to worry about.

print(df["tier"].value_counts())

You want at least ~150 sequences in Tier 1 and at least ~150 in Tier 2. If either falls short:

  1. Relax the CD-HIT threshold from 90% to 95% and re-run Step 1.3 to recover more sequences.
  2. If still short, plan for 2-fold leave-source-out instead of 3-fold later, and write this down as a documented limitation — don't hide it.
Checkpoint You have a printed count per tier and a decision (proceed as planned, or fall back to 95%/2-fold) written down in your notes.
STEP 1.6

Create homology-safe leave-source-out splits

A plain random 80/20 split lets near-identical peptides sit on both sides of the split, which will make your model look better than it really is. Instead, use GraphPart/HESTIA (reused from the AutoPeptideML reproducibility archive) at a 40% identity threshold, and rotate which source database is held out.

# pip install graphpart  (or clone from the AutoPeptideML repo's scripts/ folder)
graphpart fasta merged_cdhit90.fasta --threshold 0.40 --out-file lso_folds.csv

You want three folds: train on AnOxPePred + BIOPEP-UWM, test on held-out DFBP; then rotate so each of the three source databases gets held out exactly once. Multi-AOP and Peptipedia sequences fall into whichever fold their nearest homolog lands in.

Checkpoint You have AOP-BenchPos.csv with columns sequence, source_db, tier, lso_fold — this file is Phase 1's whole output, and every later phase reads from it.
Phase 2

Turn peptides into numbers

Two representations get computed for every sequence in AOP-BenchPos: a small hand-crafted chemistry vector, and a large learned ESM-2 vector.

STEP 2.1

Compute the 15 physicochemical features

This runs entirely on your laptop CPU in seconds — no GPU needed.

# src/descriptors.py
from Bio.SeqUtils.ProtParam import ProteinAnalysis

def compute_descriptors(seq: str) -> dict:
    pa = ProteinAnalysis(seq)
    return {
        "mw": pa.molecular_weight(),
        "gravy": pa.gravy(),
        "aromaticity": pa.aromaticity(),
        "instability": pa.instability_index(),
        "charge": pa.charge_at_pH(7.0),
        # aliphatic index + 8 CTD features: use iFeature or a published
        # CTD implementation rather than re-deriving the formulas yourself
    }

If a sequence already has descriptors from Peptipedia's export, reuse those instead of recomputing — it's one less thing that can silently disagree between sources.

Checkpoint A 15-column numeric table exists, one row per AOP-BenchPos sequence, with no missing values.
STEP 2.2

Extract ESM-2 embeddings — small model first, then Colab

Test your extraction code on the 35M model locally before spending Colab GPU time on the 650M model — bugs are much cheaper to find on the fast, free model.

# src/embed.py
import torch, esm, numpy as np

model, alphabet = esm.pretrained.esm2_t12_35M_UR50D()   # swap to t33_650M later
model.eval()
batch_converter = alphabet.get_batch_converter()

def embed_sequences(seqs):
    data = [(str(i), s) for i, s in enumerate(seqs)]
    _, _, tokens = batch_converter(data)
    with torch.no_grad():
        out = model(tokens, repr_layers=[model.num_layers])
    reps = out["representations"][model.num_layers]
    embeddings = []
    for i, s in enumerate(seqs):
        per_residue = reps[i, 1:len(s)+1]
        pooled = per_residue.max(0).values if len(s) < 10 else per_residue.mean(0)
        embeddings.append(pooled.numpy())
    return np.stack(embeddings)

np.save("data/embeddings/esm2_35M.npy", embed_sequences(sequence_list))

Once that runs cleanly end to end, switch the model line to esm2_t33_650M_UR50D(), move the notebook to Colab with the T4 runtime, and cache the result straight to Google Drive so it survives the session ending.

Common mistake Don't re-run ESM-2 inside your training loop later — extract once here, save to .npy, and have the training script in Phase 4 only ever read the cached file.
Phase 3

Decide which peptides get paired together

This is the step that makes the whole approach "positive-only" — no negative examples are chosen here, only which positives count as similar to each other.

STEP 3.1

Compute physicochemical distance within each tier

For every pair of Tier 1 sequences, and separately every pair of Tier 2 sequences, compute the Euclidean distance between their 15-feature descriptor vectors (never compare across tiers here).

from scipy.spatial.distance import pdist, squareform

tier1_dist = squareform(pdist(tier1_descriptors, metric="euclidean"))

Try a few candidate distance thresholds against a small held-out validation slice and pick the one that gives you a reasonable number of pairs per anchor — not so tight that most sequences get zero partners, not so loose that it stops meaning anything.

Checkpoint You can state, in one sentence, the distance threshold you chose and why.
STEP 3.2

Build the positive-pair list

A pair qualifies only if both conditions hold: same tier (1-with-1 or 2-with-2, never mixed), and within the distance threshold from Step 3.1.

pairs = []
for tier_df in [tier1_df, tier2_df]:
    dist = squareform(pdist(tier_df[descriptor_cols], metric="euclidean"))
    close = np.argwhere((dist > 0) & (dist < THRESHOLD))
    for i, j in close:
        pairs.append((tier_df.index[i], tier_df.index[j]))
Checkpoint A saved pair list (indices or sequence IDs), and every pair in it can be traced back to a matching tier and a distance under your threshold.
Phase 4

Build and train the model

The actual novel part of Component 1: a contrastive loss with no negative term, kept honest by three prototype anchors.

STEP 4.1

Implement the positive-only loss

Standard supervised contrastive loss compares an anchor-positive pair against every negative in the batch. Here, that negative term is simply removed — the loss just pulls the anchor and its positive closer together.

# src/model.py
import torch, torch.nn.functional as F

def positive_only_loss(anchor, positive, tau=0.07):
    anchor = F.normalize(anchor, dim=-1)
    positive = F.normalize(positive, dim=-1)
    sim = (anchor * positive).sum(-1) / tau
    return -sim.mean()   # no denominator, no negatives
Common mistake This loss on its own is happy to collapse every embedding to the same point — don't train with it until Step 4.2's diversity term is wired in.
STEP 4.2

Implement the three mechanism prototypes

One prototype vector each for FRS, MC and GEN. They start at each group's embedding centroid and track the model with an exponential moving average (EMA). Separately, a push-away term is added to the training loss so the model actively keeps the three mechanism regions apart.

class Prototypes:
    def __init__(self, init_centroids, ema=0.99):
        self.vectors = {k: F.normalize(v, dim=-1) for k, v in init_centroids.items()}
        self.ema = ema

    def update(self, tier, batch_mean_embedding):
        # detached EMA buffer — NOT part of the training graph.
        old = self.vectors[tier]
        new = self.ema * old + (1 - self.ema) * batch_mean_embedding
        self.vectors[tier] = F.normalize(new, dim=-1)

    def push_away_loss(self, embeddings, tier, lam=0.1):
        # embeddings must be the LIVE (non-detached) batch output of
        # projection_head, so gradient actually reaches the trainable
        # weights. Pulls this batch's embeddings away from the OTHER
        # two tiers' current prototypes.
        other = [v for k, v in self.vectors.items() if k != tier]
        sim = sum(F.cosine_similarity(embeddings, o.unsqueeze(0).expand_as(embeddings)).mean()
                   for o in other)
        return lam * sim

    def pairwise_distance_report(self):
        # diagnostic only, for the Step 4.4 collapse check — not part of the loss.
        keys = list(self.vectors.keys())
        return {f"{keys[i]}-{keys[j]}": (1 - (self.vectors[keys[i]] * self.vectors[keys[j]]).sum()).item()
                for i in range(len(keys)) for j in range(i + 1, len(keys))}
Why this changed An earlier version of this guide computed the diversity term purely from self.vectors (the EMA buffers) and added it straight to the loss. Because those buffers are built from .detach()'d embeddings, that term carried no gradient back to projection_head — it would silently do nothing during training. push_away_loss fixes this by computing the term from the current batch's live embeddings instead, so it actually influences training; pairwise_distance_report is now the separate, EMA-based signal you log for the Step 4.4 collapse check.
Checkpoint Calling prototypes.pairwise_distance_report() right after initialisation shows three clearly different, non-collapsed distances (not near 0).
STEP 4.3

Write the training loop

Batch size 64 positive pairs, max 100 epochs, early stopping with patience 10 on a held-out validation slice. This is the step that only ever touches cached .npy embeddings — it does not load ESM-2 at all, which is why it's fast even on a laptop.

# src/train.py
projection_head = torch.nn.Linear(1280, 128)   # ESM-2 650M dim -> 128-D output
optimizer = torch.optim.Adam(projection_head.parameters(), lr=1e-3)

for epoch in range(100):
    for anchor_idx, positive_idx, tier in pair_batches:
        a = projection_head(esm_embeddings[anchor_idx])   # live, NOT detached
        p = projection_head(esm_embeddings[positive_idx])
        loss = positive_only_loss(a, p) + prototypes.push_away_loss(a, tier)
        optimizer.zero_grad(); loss.backward(); optimizer.step()
        prototypes.update(tier, a.mean(0).detach())        # EMA buffer update, detached on purpose
    val_score = evaluate_on_validation_fold()
    early_stopper.step(val_score)
    if early_stopper.should_stop: break

Note the two different roles here: push_away_loss(a, tier) uses the batch's live embedding a so the optimiser can actually act on it, while prototypes.update(...) immediately after uses a detached copy — the EMA buffer is meant to track the space, not be trained by gradient descent directly. Mixing these up (detaching the loss input, or not detaching the EMA input) is the easiest way to silently break this step.

Checkpoint Training loss goes down over the first few epochs and doesn't hit NaN.
STEP 4.4

Watch for prototype collapse while training

Log the pairwise cosine distance between all three prototypes every epoch, using the diagnostic method added in Step 4.2. If any pair drops below 0.1, the push-away term isn't strong enough yet.

# append inside the epoch loop, after prototypes.update(...) calls
print(epoch, prototypes.pairwise_distance_report())
  1. Increase lam from 0.1 to 0.5 in push_away_loss.
  2. Re-initialise the prototypes (ideally with an orthogonal initialisation) and restart training.
Common mistake Don't discover a collapse only after training finishes — check the logged distance plot at epoch 10, not epoch 100.
Phase 5

Prove it actually works

A trained model isn't evidence by itself — these are the specific numbers your report and presentations need.

STEP 5.1

Recall@K and nDCG@10 on the LSO folds

For every held-out query peptide, retrieve its K nearest neighbours by cosine similarity in the 128-D space and check how many actually share its mechanism tier.

from sklearn.metrics import ndcg_score
from sklearn.metrics.pairwise import cosine_similarity

sims = cosine_similarity(query_embeddings, gallery_embeddings)
top_k = sims.argsort(axis=1)[:, -10:]
recall_at_10 = (query_tier[:, None] == gallery_tier[top_k]).any(axis=1).mean()
Checkpoint A Recall@10 and nDCG@10 number for each of the three LSO folds, not just one averaged number.
STEP 5.2

Prototype purity (K-means, K=3)

from sklearn.cluster import KMeans

clusters = KMeans(n_clusters=3, n_init=10).fit_predict(all_embeddings)
purity = compute_purity(clusters, true_tiers)   # fraction matching majority label per cluster
Checkpoint A purity score above roughly 0.7 is the signal the embedding space genuinely separated by mechanism.
STEP 5.3

Prove homology leakage would have inflated your results

Retrain the exact same model, but this time evaluate on a plain random 80/20 split instead of the LSO folds. Compare Recall@10 between the two. If the random split scores higher, that gap is the leakage inflation — and reporting that number honestly is itself one of this component's contributions (HP4).

Checkpoint Two Recall@10 numbers side by side: LSO vs. random split, with the difference stated explicitly.
STEP 5.4

Run the statistical tests properly

from scipy import stats

stat, p = stats.wilcoxon(lso_scores, random_split_scores)
stat2, p2 = stats.mannwhitneyu(fused_purity_scores, esm_only_purity_scores)

Report the p-value and an effect size (Cohen's d or rank-biserial correlation) for every result you call significant — a p-value alone doesn't tell your supervisor how big the difference actually is.

Checkpoint Every claim in your results section has a test name, a p-value, and an effect size attached to it.
Phase 6

The scaling ablation (HP5)

Does a bigger ESM-2 model actually make the representation better, or does the benefit plateau early? This is the last thing to do, once the primary 650M pipeline is proven to work end to end.

STEP 6.1

Repeat Phases 2–5 for 150M and 3B

Same code, same pair list, same training procedure — only the ESM-2 checkpoint changes. Run esm2_t30_150M_UR50D on your laptop, and esm2_t36_3B_UR50D on Colab (drop the batch size to 16–8 if you hit an out-of-memory error on the T4).

Checkpoint Four nDCG@10 numbers, one per backbone size (35M, 150M, 650M, 3B), all evaluated the same way.
STEP 6.2

Correlate model size against performance

Spearman correlation between log parameter count and nDCG@10, plus pairwise Wilcoxon tests between adjacent sizes (35M vs 150M, 150M vs 650M, 650M vs 3B).

Checkpoint A one-sentence answer you can say out loud: "scaling helped up to X, then plateaued" or "scaling made no significant difference" — either is a valid, reportable finding.
